# Twelve-servo motion execution handoff

2026-09-16. This supplement adds phase timing, joint coordination, engagement,
interruption and electrical scheduling requirements to the twelve selected motion
sources. The original Blender demonstrations, sampled trajectories, command names
and archived source packages are preserved.

The files are geometric research inputs for the firmware/body-control agent.
`timing.py` is an offline clock reference; it neither emits servo commands nor
activates a physical operating profile.

## Timing profiles

- `demonstration`: the approved source durations, including inspection holds.
- `research_candidate`: independently editable phase durations; initially copies
  the demonstration. `--scale 2` explores twice the playback rate without changing
  any file. These timings are unqualified for hardware.
- `operating`: phase durations and calibration identity are `null` until loaded
  actuator measurements and trajectory evaluation support a chosen operating
  profile. Null means unknown, not zero or unlimited. Filling these fields does
  not implement or arm an executor. The offline utility deliberately refuses this
  profile.

Run from this directory; Python 3 and its standard library are sufficient:

```bash
python3 timing.py contracts/wave.json --profile research_candidate --scale 2 --time 3
python3 timing.py contracts/walk.json --cycles 3 --time 16.2
python3 -B -m unittest -v test_timing.py
```

The Wave example yields an 8-second research schedule and samples source time 6 s
at execution time 3 s. Its stand-face cue moves from 15.2 to 7.6 s. With uniform
2× speed, requested joint speeds double and accelerations quadruple. No faster
Blender preview or servo execution is generated by this clock utility.

For selective adjustment, edit a **copy** of a contract's
`timing_profiles.research_candidate.duration_s`. For example, shorten the six
`p003_shoulder_wave_1` through `p008_shoulder_wave_6` phases from 0.6 to 0.4 seconds
while retaining the seated entry and foot replacement durations. That is a
14.8-second research schedule. Its peak clock rate can exceed the ratio of the
old/new phase durations, because boundary velocities remain continuous.
The catalog checksums identify the original delivery; a changed candidate needs
its own identifier and checksum before integration.

### One clock for all motion data

Sample all twelve joints, body pose, foot targets and contacts at the same source
time `s(t)`. Discrete events use that clock too; `event_times()` maps source event
times to execution times. A sample interval of 1/120 s describes the source data,
not the PWM frequency or a guaranteed mechanical response time.

For a source phase of length `L`, execution duration `D` and fraction `u`, the
reference uses a shared boundary rate `r = min(L / D)` over the schedule:

```text
s(t) = phase_source_start + r D u + (L - r D) (10u³ - 15u⁴ + 6u⁵)
q_velocity     = q_source_derivative × s_velocity
q_acceleration = q_source_second_derivative × s_velocity²
                 + q_source_derivative × s_acceleration
```

This monotone time map has matching first and second derivatives at adjacent
phase boundaries. It preserves uniform scaling exactly and avoids abrupt clock
rate changes when individual phase durations differ. Existing joint curves are
monotone cubic with C1 continuity (matching positions and velocities); their
accelerations can still jump at source knots. A smooth clock alone cannot fix
that. Recompute extrema after retiming and refine the source where calibrated
acceleration/jerk requirements demand it.

Per-phase `reference_peak_speed_rad_s` and
`reference_peak_acceleration_rad_s2` use analytic extrema of the full source's
monotone cubic joint interpolation. They are **requested kinematic demands**, not
measured servo limits. Walk needs its existing matched seam tangents applied before
computing final compiled demands. Firmware sampling, tracking lag and pulse/update
cadence still require evaluation.

### Walk loop handling

The current source has an established continuous whole-body gait; this supplement
preserves it. Use entry source seconds 0–12.2, repeat source seconds 12.2–16.2, then
use the existing phase-matched exit at source seconds 24.2–32.4. One steady cycle
advances 99.2 mm. Preserve the canonical compiler's entry/loop/exit tangents.

Use the existing loop translation rule for every world-space body, foot, contact
and COM field. Rebase the exit to the actual number of completed cycles. Row 480
is the interpolation closing knot, not an additional held sample. `timing.py`
reports a cycle index and source time only; it does not translate geometry or
replace the loop-aware sampler. Loop source-time resets represent periodic
sampling, not joint-angle jumps.

## Coordination and electrical scheduling

The [shared policy](execution-policy.json) defines all defaults and required
measurements. Flat joint ordering is leg-major:

```text
FL: h_Part002, alpha_Part006, theta_Part005
FR: h_Part002, alpha_Part006, theta_Part005
RL: h_Part002, alpha_Part006, theta_Part005
RR: h_Part002, alpha_Part006, theta_Part005
```

CAD FL/FR are physical rear-left/rear-right; CAD RL/RR are physical
front-left/front-right in these sources. Angles are signed geometric radians;
positions are millimeters; time is seconds. Passive lower-link angles come from
four-bar closure and are not extra servo outputs.

Keep the three actuators of each leg coordinated, including Part005 and Part006,
and retain coordination between supporting legs and the body. Intentional
per-joint trajectory delays remain zero. Adding such delays changes the foot path
and requires renewed mechanical/contact checks.

Firmware should expose these distinct controls:

1. **Initial engagement:** configurable activation groups/order and spacing from a
   known supported pose. Values remain unmeasured. Ordinary movement does not
   repeatedly detach supporting servos.
2. **PWM pulse phases:** configurable channel start offsets that preserve each
   calibrated pulse width, including counter wrap. The observed P4 driver uses
   50 Hz and zero ON counters, so pulse staggering is a remaining implementation
   requirement. Even spacing would be 20,000/12 µs between starts, only a candidate
   experiment, not a selected hardware setting.
3. **Target update timing:** one trajectory clock with an explicit sample/hold or
   phase-compensated policy. Measure update latency and inter-joint tracking skew;
   do not silently turn pulse offsets into arbitrary motion delays.

PCA9685 permits independent channel pulse timing. Servo input pulses do not
directly describe motor current; staggering them does not establish brownout
protection. Measure rail voltage/current during loaded starts, reversals and
holds, then configure limits and scheduling in the existing P4 actuator owner.
References: [NXP PCA9685 datasheet](https://www.nxp.com/docs/en/data-sheet/PCA9685.pdf),
[Pololu servo control interface](https://www.pololu.com/blog/17/servo-control-interface-in-detail).

## Entry, interruption and completion

Contracts record exact entry joint angles, body pose and contact state. If the
current pose differs, create a coordinated contact-aware transition; do not jump
to the first sample. A commanded pose is not measured position feedback. Unknown
physical pose requires supported recovery.

An ordinary interruption must brake from the current phase while preserving
coordination. If a foot is raised, choose a supported placement or hold from that
state. Seeking directly to the last row is not an interruption strategy. Resume
through a matched transition. Keep the existing independent emergency-disable
path. Finishing source playback does not prove physical pose completion.

Travel, loaded speed, acceleration, braking, jerk, tracking skew and electrical
limits remain configurable unknowns. Respond to an infeasible candidate by
slowing coordinated motion or regenerating its path, not by independently
clamping servos. Existing balance/collision limitations remain attached to each
source; some walking/turning support margins are negative under their assumed COM.

## Reproduction and evidence

`build_contracts.py --repo /path/to/Ainekio` regenerates the JSON from the bound
sources and requires NumPy. It overwrites generated contract files, so preserve
edited candidate profiles separately. No Blender, firmware or live hardware is
needed for this build.

Physical calibration, electrical scheduling implementation, arbitrary-pose
transitions and loaded execution remain work for the existing firmware owner.
